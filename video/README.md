# `video/` — the Home SOC walkthrough film

Everything in this folder exists to produce one file:

```
video/out/HomeSOC-walkthrough.mp4      1920x1080 · 30 fps · H.264 + AAC · 16 min 23 s
video/out/HomeSOC-walkthrough.srt      one cue per sentence, timed to the finished cut
```

It is a **narrated screen walkthrough**, generated by scripts rather than edited by hand, so it can
be regenerated after the product changes instead of going stale. Nothing here is part of the
product: `homesoc/**` is read, never written. The film runs against its own seeded database in
`video/demo_data/` and **never touches `data/` or `config.toml`**.

The contracts that govern it are `video/CONTRACT.md` (v1: narration, cursor, compositing, encoding)
and `video/CONTRACT_V2.md` (v2: the 20-scene plan, the Lens act, the phone rig, the scan rig).

---

## Regenerating it

```bat
:: everything, from an empty build directory
python video/render.py

:: iterate on one scene (re-captures and recomposes only that one)
python video/render.py --only 18-lens-scan

:: recompose from the shots already on disk - no browser, no network
python video/render.py --no-capture --no-narrate --no-seed

:: what the scenes are, and how long each one's narration is
python video/render.py --list
```

A cold run is roughly: seed a few seconds, narrate a couple of minutes (network, cached after the
first run), capture several minutes (two browser contexts plus the scan rig), compose a few minutes.
Repeat runs are much faster: every scene clip is fingerprinted, and only the scenes whose shots,
timings, plan or compositor actually changed are re-encoded.

`render.py` prints a per-scene progress line with frames, seconds, encode speed, elapsed time and an
ETA, and finishes with an `ffprobe` check of the deliverable.

## The modules

| file | what it owns |
| --- | --- |
| `seed_demo.py` | builds `video/demo_data/homesoc.db` — a fictional household: 18 devices, a believable finding lifecycle, DNS history, a paired Lens phone and its tags. Idempotent; never writes to `data/`. |
| `script.py` | `SCENES`: the narration text and the on-screen choreography, as data. No logic. |
| `narrate.py` | edge-tts → `build/audio/scene_NN.mp3`, `build/timings.json`, and the SRT. Cached by a hash of (text, voice, rate). |
| `slides.py` | the full-frame HTML cards: title, what-it-is, architecture, first run, day-to-day, **the Lens gap**, **Lens identification**, **Lens honest limits**, close. Rendered by `capture.py` in the same browser as the dashboard, so they share the product's palette and type. |
| `scene_render.py` | the illustrated scene for the scan shot — a camera on a shelf with a **real** QR sticker from `homesoc/web/qr.py` — and the Y4M camera clip with its handheld drift. |
| `decode_sidecar.py` | a loopback HTTP endpoint that decodes a PNG with zxing-cpp. Capture-time only (see below). |
| `phone.py` | drives `/lens` in a 390x844 @3x mobile context, and draws the phone body a screen is composited into. |
| `capture.py` | Playwright + the installed Chrome → `build/shots/*.png`, `build/geometry.json`, `build/shots_manifest.json`. Owns the demo server subprocess, the scan rig and the `BarcodeDetector` shim. |
| `compose.py` | the look. Turns shots + geometry + narration lengths + actions into frames, in memory, piped to ffmpeg as raw `rgb24`. Cursor, ripple, tap, highlight, zoom, scroll, captions, dissolves. |
| `render.py` | the orchestrator: seed → narrate → capture → **scan-rig check** → compose → concat → mux → verify. `--only`, `--no-capture`, `--force`, `--list`. |
| `shoot_docs.py` | unrelated to the film: the screenshots used by `docs/`. |

Intermediates live in `video/build/` (gitignored): `shots/`, `audio/`, `clips/`, `timings.json`,
`geometry.json`, `shots_manifest.json`, `timeline.json`.

## Tools this needs (development only)

None of these are runtime dependencies of Home SOC. The product still installs `flask`, `requests`
and `dnslib` and nothing else.

| tool | why | install |
| --- | --- | --- |
| **ffmpeg / ffprobe** on `PATH` | encoding and verification | any recent full build |
| **Playwright** + the **installed Chrome** | capture. The bundled browser download fails on this machine, so every launch is `p.chromium.launch(channel="chrome")` | `pip install --user playwright` |
| **edge-tts** | the narration voice (`en-US-AndrewMultilingualNeural`, `-4%`). Needs the network on a cold run | `pip install --user edge-tts` |
| **Pillow**, **numpy** | frame compositing | `pip install --user pillow numpy` |
| **zxing-cpp** | the capture-time decode sidecar, below | `pip install --user zxing-cpp` |

**`zxing-cpp` must never appear in `requirements.txt` or `pyproject.toml`.** It is a tool used while
recording the film, in the same way ffmpeg is; the product has no barcode decoder and does not need
one, because on a phone the decoding is done by the browser.

## The scan scene is recorded with a decode sidecar — and the pixels are really decoded

Required disclosure (CONTRACT_V2 §V3).

Lens identifies a device by decoding a visual tag with **`BarcodeDetector`**, a browser platform API
that Chrome provides **on Android, macOS and ChromeOS — but not on Windows**. The machine this film
is recorded on is a Windows PC, so the in-browser decode that the real product performs on a phone
cannot run here.

The scan scene is therefore recorded like this:

1. `scene_render.py` draws the scene — a small camera on a shelf with a QR sticker on it — as
   HTML/SVG in the same browser. The sticker is a **real QR code**, produced by the product's own
   encoder (`homesoc/web/qr.py`), encoding the demo camera's **real sticker token** from the seeded
   database.
2. That still becomes a short **Y4M** clip with a slow handheld drift, and Chrome is launched with
   `--use-file-for-fake-video-capture=<clip>.y4m`, so the camera feed Lens opens *is* that scene.
3. `decode_sidecar.py` runs a loopback HTTP endpoint that decodes a PNG with **zxing-cpp**.
4. Playwright injects a `BarcodeDetector` shim that grabs the frame the page is displaying, posts it
   to the sidecar, and returns the decoded value and bounding box in the shape the real API returns.

So **the code on screen is genuinely decoded from the pixels on screen**. Nothing is faked, replayed
or hard-coded: the token that appears came out of a decoder that read the frame. The only
substitution is *where the decoder lives* — beside the browser instead of inside it.

### Two recording aids in the same scene, also disclosed

**The viewfinder is captured as a burst, not as one screenshot.** A `Phone`/`PhonePair` shot may
carry `burst=N, burst_ms=M`; `phone.py` then takes N screenshots M milliseconds apart and
`compose.py` plays them back (forwards, then backwards, so the loop never cuts). Without it the
handheld drift that step 2 above bakes into the Y4M never reaches the film at all — the v2 cut's
"money shot" was a still photograph held for thirty-three seconds under narration that says "hold
still" and "Lens reads frames the whole time". Every frame of a burst is a real screenshot of the
real page; nothing is interpolated.

**One endpoint is deliberately slowed by a few seconds, once.** Between decoding a code and opening
the card, Lens shows a real state: the reticle's four corners turn green and the chip reads
"identifying…" while `/api/lens/identify` is in flight. On loopback that answers in single-digit
milliseconds, so the state exists for about two frames and cannot be photographed. A `Phone` shot
with `hit=True` makes `phone.py` hold *the response to that one endpoint* back for `hit_ms` (see
`_LATENCY_JS`), photograph the page, and release it. The decode is real, the request is the page's
own, the answer is the server's, and the pixels are the product's — the only thing changed is how
long the network took. `phone.py` **fails loudly** if the reticle's own 600 ms window closes before
the shutter, so this can never silently become a still of an idle viewfinder.

Two things enforce that this stays true:

* `capture.py` **fails** if the shim does not return the scene's sticker token. It will not fall
  back to the manual picker and let the narration call it a scan.
* `render.py` re-checks it from `build/shots_manifest.json` before composing — including on
  `--no-capture`, where nothing else would look at a reused shot. The only way past it is
  `--no-scan-check`, which prints a warning saying the render must not be published.

The narration is written to describe **the product**, not the recording: "point the phone at the
sticker and Lens recognises it" is true of Chrome on Android, which is the target platform. Nothing
in the film claims to be running on a phone.

## Honesty rules the whole film is held to

* No frame shows the author's real network: no real MAC, hostname, SSID, public IP, or a path
  containing a username. The demo host is `HOME-PC`, the SSID `Home-WiFi`, the public IP
  `203.0.113.42` (RFC 5737 documentation range).
* Every number spoken matches what is on screen at that moment, in the seeded database.
* Nothing claims a capability the product does not have. It is not an antivirus engine, not an EDR,
  not an IDS, and Lens is not world-anchored AR — it is a camera viewfinder with an information
  panel, and `slides.lens_limits()` says so out loud in the film itself.

## Notes for whoever edits this next

**Slide names.** `script.py` refers to slides by the keys of `slides.SLIDES`:
`title`, `what_it_is`, `architecture`, `first_run`, `daily_use`, `lens_why`, `lens_how`,
`lens_limits`, `close`. `slides.render()` also accepts a few aliases (`lens_identify`,
`lens_honest`, …); `capture.py` looks the name up in `SLIDES` directly, so prefer the canonical
spelling. `lens_limits` — the honest-limits card CONTRACT_V2 §19 asks for — closes scene 19: the
card scrolls to "Talking to", then the film cuts to the slide for the three limits the voice lists.

**Numbers are read, not typed.** Anything the film states twice — once in the voice and once on a
slide — is derived at build time from the same source, because every literal that was typed by hand
had gone stale by the time anyone looked. `script.catalogue_counts()` feeds both the spoken rule
count in scene 3 and the CATALOGUE tile on the architecture slide (88 / eighty-nine / 92 was a
three-way disagreement). `slides._schema_version()` fills the first-run terminal, whose log lines are
also stamped relative to now. `slides._camera_row()` and `slides._device_count()` read
`video/demo_data/homesoc.db`, so the "gap" slide's port chips and device age track the seed instead
of contradicting the pages three minutes later. `script._dns_24h()` does the same for the two DNS
shares the voice speaks, which move every hour because the seed is relative to now. If you are about
to type a number into this package, read it from somewhere instead.

**The lower third is a lower third.** `compose.CAPTION_HOLD` (5.6 s) is how long the caption pill
stays up before it fades, not how long the scene runs. The pill is ~300 CSS px wide — about 60 px
past the sidebar — so holding it for a 65 s scene parked an opaque box on top of page content: it ate
the leading "W" of `WIN-ACC-005`, blanked a hostname cell under a Zoom, and covered the "BY CATEGORY"
heading on `/summary`. Its sidebar-footer backdrop is only painted over states that actually *have* a
sidebar (`ScenePlan.sidebar_states`); `/lens/pair` and `/lens/stickers` have none, and repainting one
there drew a hard-edged grey rectangle behind the caption for a whole scene.

**PhoneScroll needs to be told what scrolls.** `phone.py` records the `#card-body` rect as
`scroller` on every `card` shot, and `PhoneStore._scroll_band` uses it. Do not go back to inferring
the fixed rows by differencing two scroll states: the rows above the Lens card are a *live camera
feed*, so two captures are never identical up there, no fixed band is detected, and the whole screen
gets stacked — which tore the card in half mid-scroll, header text above a band of viewfinder above a
second drag handle.

**Slide overflow.** Every `<text>` in the architecture diagram carries `data-maxx`.
`slides.overflow_probe()` returns a one-liner that checks all of them in the page — a reworded label
can never silently overrun its box.

**What the compositor expects from capture.** `build/shots_manifest.json`, per scene, in
chronological order:

```jsonc
{"index": 0, "kind": "phone_pair", "path": "/lens", "scroll": 0, "png": ".../18-lens-scan_0.png",
 "phone": {"state": "scan", "scene_png": ".../scene_camera.png", "aim": [0.50, 0.35],
           "via": "scan", "expected_code": "hs1:…", "decoded": "hs1:…"}}
```

* `kind` is `page`, `slide`, `phone` or `phone_pair`.
* Phone metadata may be nested under `"phone"` (what `capture.py` writes) or flat on the row.
* `scene_png` is required for `phone_pair`; without it the compositor fails loudly rather than
  drawing half a shot. If it is missing the compositor also looks for `<shot>_scene.png` beside the
  phone shot, which is what a hand-made fixture can provide.
* `aim` is where in that illustration the phone is pointed, as fractions of the image; it defaults
  to the sticker's position in `scene_render.py`'s frame.
* `expected_code` / `decoded` are the scan-rig proof described above.

**Phone geometry.** A phone shot is captured at 390x844 @3x and the finished frame is downscaled
exactly once. The phone **body** (not the framed image, which includes a drop shadow) stands at 70%
of frame height in phone-only shots and 68% in the pair shot — inside CONTRACT_V2 §V5's 55-70%, and
high enough in it that the Lens screen lands at 0.87x its own CSS pixels, so 15 px body text arrives
as 13 px on the finished frame.

**Verifying the compositor on its own**, with no browser, server or capture run:

```bat
python video/compose.py --selftest         :: cursor, click ripple, highlight, scroll, zoom, caption
python video/compose.py --selftest-phone   :: phone shot, Tap, PhoneScroll, PhonePair, dissolve
```

Both draw their own fixtures under `video/build/selftest/` and leave probe PNGs
(`probe/`, `probe_phone/`) to look at. Look at them — that is the point of them.
